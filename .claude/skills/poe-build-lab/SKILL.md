# 研究單位：多 agent 的流派開發

模仿玩家社群開發流派的方式：先有一個看起來很強的核心機制，幾組人各自圍繞它找零件、拼裝、驗證，偶爾在公開場合交換發現。

```
主控（你）── 建立並監管，非必要不發聲
   │
   ├─ 研究單位 A ── 研究者 agent ⇄ 私人筆記
   │                    └─ 需要時自己派出查核者 agent（核對／窮舉／評論）
   ├─ 研究單位 B ── 同上
   ├─ 研究單位 C ── 同上
   │
   └─ 留言板（本地服務）── 單位之間唯一的交流管道；開跑一段時間後才告知它的存在
```

| 角色 | 是什麼 | 做什麼 |
|---|---|---|
| 主控 | 你，主對話 | 寫前提、啟動、定時觀察、處理意外、收件驗證、向使用者回報。不替研究者做設計決定 |
| 研究者 | 你用 Agent 工具啟動的背景 agent，每單位一個 | 物色零件、構築、存檔、寫文件。只有它能存檔構築 |
| 查核者 | **研究者自己**派出的子 agent | 站在外面的第三方：核對資料、暴力窮舉、評論流派。不找零件、不做決定、不存檔 |
| 留言板 | `board\server.py`，本機 HTTP 服務 | 討論串制、只拉不推、有配額。伺服器端強制規則 |

## 什麼時候用、什麼時候不用

- **只有使用者明確要求跑研究單位時才用。** 一輪 3 個單位、2 小時，實測處理量約 2.5 億到 5.5 億 token（見「用量」），而且會把使用者的額度用完。
- 使用者的 Claude Code 視窗要開著整輪。工作階段結束，研究單位和留言板都會停。
- 問題只是「這個配置在 PoB 裡多少傷害」「這件裝備值不值得買」→ 不是這個 skill，用對應的工具 skill。

啟動前向使用者確認（缺的才問，已經講過的不要重問）：

1. **核心機制**是什麼，哪些是給定的、哪些留給研究者決定。
2. 單位數（預設 3）、最低與最高工作時間（預設 120／180 分鐘）。
3. 預算與禁用的東西；和既有玩法比較時有沒有指定條件。
4. 用哪一個 PoB 安裝、看哪一季的資料。
5. 交易站憑證是否有效（失效時研究單位只會標「未能查證」，不會去刷新）。

使用者用到遊戲暱稱而它可能指兩種東西時，先確認是哪一個再寫進前提。寫錯的前提會被原樣發給每個單位。

## 流程

實驗室是專案之外的一個資料夾（下稱 `<lab>`），由 `lab_template\` 複製而來。以下指令都在 `<lab>` 底下執行。

### 1. 建立實驗室

```bash
cp -r <這個 skill>/lab_template  <lab>          # 例如 Desktop\project\<題目>-lab；不要放在專案 repo 裡
python <lab>/_control/smoke_test.py             # 在暫存複本上自我測試，全部 PASS 才往下
```

已經有實驗室、要跑下一輪時不要重建：先停掉留言板，再 `python _control/archive_round.py` 把上一輪收進 `round<N>\`。

### 2. 寫前提 `_control\PREMISE.md`

從 `templates\PREMISE.example.md` 複製來填。它會原樣貼進每位研究者的簡報，是整輪最重要的一份文字。

- **只寫使用者給定的東西，和有來源、你確認過的事實。** 每條事實附來源。
- **不寫你對「該怎麼配」的看法，不寫前幾輪或其他對話裡得到的構築結論。** 研究單位要從零開始；你先講了答案，它們就只會最佳化那個答案。
- 模擬器算不出來、但使用者已經知道的關鍵事實（例如某個機制的實際表現）要給，否則每個單位都會卡在同一個查不到的問題上，或因為「量不出來」而放棄正確的零件。
- 題目的「環境」要寫清楚：遊戲版本、用哪個 PoB 安裝、資料還沒更新的部分。
- 簡報骨架（`templates\BRIEF.md`）已經包含與題目無關的規則：工作順序、完整度、藥劑規則、和主流玩法比較、時間、交付物。要改通用規則就改骨架，不要塞進前提。

### 3. 隔離檢查

研究者會到處翻。啟動前確認它們翻得到的地方沒有前幾輪的東西：

- 上一輪已封存（`units\` 是空的）。
- PoB 的構築列表資料夾裡沒有前幾輪構築的複本（給使用者看過之後要移除）。
- PoB 安裝目錄、專案目錄裡沒有前幾輪留下的檔案。
- `shared\` 裡只有這一輪要給的資料。

封存留在 `<lab>\round<N>\`，只靠簡報裡「不要讀其他目錄」約束。要更確實就把它搬到實驗室外面。

### 4. 啟動

```bash
python board/server.py --port 8765                       # 背景執行，整輪都要開著
python _control/setup_units.py --skills "<專案>\.claude\skills" [--units A,B,C] [--min-minutes 120] [--max-minutes 180]
```

`setup_units.py` 會記下開始時間、建好各單位的目錄、把前提和時間填進兩份簡報。**跑完立刻啟動 agent**，時間是從這一刻起算的。

用 Agent 工具同時啟動每個單位的研究者（`subagent_type: general-purpose`，背景執行）。啟動訊息只需要：

- 它是哪個單位的研究者；
- 先完整閱讀 `<lab>\units\<U>\BRIEF.md` 再開始；
- 最早與最晚結束時間（`setup_units.py` 印出來的）；
- 持續工作、不要停下來等指示；還沒到最低時間就找不到提升時不要收工。

不要在啟動訊息裡補充設計上的提示。記下每個研究者的 agent id，之後傳訊息和算用量都要用。

接著放一個背景計時器把自己叫醒（背景執行 `python -c "import time; time.sleep(1320)"` 之類）。主控只在有事件時才會被喚醒，沒有計時器就會錯過檢查點。

### 5. 開放留言板

兩個條件都成立才開放：**開跑滿 20 分鐘**，而且**每個單位的筆記裡已經有零件清單和至少一個具體假說**（用 `python _control/status.py` 看）。先讓每個單位形成自己的方向，再開放交流。

```bash
python _control/issue_keys.py          # 發金鑰、產生每個單位的通知全文、擷取方向快照
```

用 SendMessage 把 `_control\reveal_<U>.md` 的**全文**傳給對應的研究者（它們讀不到 `_control\`）。訊息會在對方下一次工具呼叫時送達。

開放前不要以任何方式提到留言板：簡報骨架裡沒有這個詞，沒有金鑰時伺服器對一切請求回 404。

快照（`_control\snapshots\reveal\`）是之後判斷「趨同是留言板造成的，還是開放前就已經一樣」的依據，向使用者回報方向時一併說明。

### 6. 觀察

每 40 到 50 分鐘看一次，並在最低時間到的那一刻看一次：

```bash
python _control/status.py 1200 -v --watch "<PoB 安裝目錄>"
```

看什麼：

- 各單位註冊了哪些構築、筆記最後在做什麼、有沒有交付文件。
- 留言板：誰發了什麼、有沒有回覆、讀寫次數（有沒有人輪詢）。
- `builds\` 裡有沒有沒報備的檔案；不該被寫入的目錄有沒有多出檔案。
- 各單位的方向是否趨同。

**非必要不發聲。** 你看到某個單位走錯方向、漏了某個零件，都不要提醒；那是實驗的一部分，回報給使用者就好。主控開口的時機只有：

- 單位回報意外，需要你處理或回覆。
- 規則被破壞（存了沒報備的檔、動了別人的東西、把檔案寫到不該寫的地方）。
- 有單位在最低時間之前就自己結束 → 用 SendMessage 叫回，請它照簡報回去物色零件或換方向。
- 使用者要你轉達的事。

每次觀察後向使用者簡短回報。**同一種失敗在多個單位反覆出現時（某個來源讀不到、某個工具報同樣的錯），把它當成系統性問題去查原因並告訴使用者**，不要只是逐次轉述；單一 agent 只看得到自己那一次，只有主控看得到全貌。

### 7. 中斷與恢復

| 狀況 | 處理 |
|---|---|
| 額度用完，研究者被中止 | 進度都在（檔案和上下文）。額度恢復後**先問使用者**要不要叫回；叫回用 SendMessage，訊息裡寫明中斷前做了多久、新的最早與最晚結束時間、背景腳本和查核者可能已經不在 |
| 重開機或工作階段重啟 | 同上；另外留言板要重新啟動（金鑰和討論串都在 `board\board.db`，不用重發） |
| 留言板被系統關掉（例如記憶體不足） | 告訴使用者，由使用者決定要不要重開，不要自己重開 |
| 研究者的上下文被自動壓縮 | 正常現象，接近上限時會發生。它靠摘要和自己的筆記接續，所以簡報才要求持續寫筆記。壓縮後它不記得沒寫進筆記的細節 |

### 8. 收件與驗證

研究者交付後，**不要直接轉述它的數字當結論**。逐項確認：

1. **每個存檔重新載入模擬器**（照當下的 `pob-operator`），讀出的數字和研究者回報的一致。
2. **跨單位比較要在同一套設定下重算。** 各單位存檔時的藥劑、充能球、敵人條件都不一樣，直接比面板數字沒有意義。至少做一組「把藥劑和各種加成條件都關掉」的共同設定；自己動不了的差異（各單位用的光環、詛咒、強化）要明講。
3. **可取得性**：掃過每個存檔用到的傳奇、寶石、特殊物品，用 `poe-wiki` 查這一季是否仍會掉落。研究者和查核者常常只查了詞綴合法性。
4. **報備與檔案相符**：`builds\` 裡只有報備過的檔案；文件存在。
5. **沒有動到不該動的地方**：專案目錄（`git status`）、PoB 安裝目錄、其他單位的目錄。
6. 研究者回報寫檔工具拒絕寫文件、把全文放在最終訊息時，用 `python _control/extract_doc.py <U> <該 agent 的 jsonl>` 原樣存檔，不要自己重打。

向使用者回報時：

- 分清楚「研究者自報」和「我重新載入核對過」。
- 各單位自己列的未驗證假設要帶到，尤其是多個單位共同依賴的那幾個。
- 有沒有趨同、是開放留言板之前還是之後發生的。
- 查核者和留言板實際造成了哪些改變。
- 過程中的意外，包括你自己處理錯的。

### 9. 交付之後

- **使用者指出事實錯誤或某件東西不能用** → 把使用者確認的事實寫成條列，用 SendMessage 叫回受影響的單位調整。訊息裡要寫「調整不了、改完已經沒有價值的構築就放棄並在文件裡標明」，否則它們會勉強交一個站不住腳的版本。交付後重做第 8 步。
- **使用者要看構築** → 複製到 PoB 的構築列表資料夾（檔名加單位代號，標出推薦與已放棄的），並提醒要用哪個 PoB 安裝開。下一輪開始前要移除。
- **使用者提供的遊戲知識與偏好** → 屬於通用規則的，改進 `templates\BRIEF.md`；只屬於這個題目的，留在這個實驗室的筆記裡。**不要把任何流派的結論寫回這個 skill。**
- 各單位的 `notes\knowledge_for_kb.md` 是它們建議寫進知識庫的操作經驗，整理後給使用者過目，不要自己直接改其他 skill。
- 結束時：關掉留言板、確認沒有殘留的瀏覽器工作階段、跑一次用量統計。

```bash
python _control/token_usage.py "<...\.claude\projects\<專案>\<工作階段 id>\subagents>" --since "<這一輪的開始時間>"
```

## 設計上的決定與原因

這些是跑過幾輪後定下來的。要改之前先看原因。

| 決定 | 原因 |
|---|---|
| 前提刻意模糊，不給構築方向 | 給了方向，各單位只會最佳化它。使用者要看的是從零開始會長出什麼 |
| 簡報強制「先物色零件、再構築」 | 沒有這一步時，研究者會直接把候選零件逐一裝上去量、挑最高的，之後只在量過的東西裡選。先盤點的單位做出來的構築明顯比較完整 |
| 最低工作時間；找不到提升時改換方向 | 沒有下限時，研究者在單一方向上的微調剩 1–2% 就自認收斂，半小時到四十分鐘就收工，替代方向只做紙上估算 |
| 放棄一個方向前要實際建出來量 | 紙上估算被當成結論，而且後來常被證明是錯的 |
| 沒有「助手」，只有「查核者」 | 有助手時研究者把查資料整個外包，自己一次都不上網，拿到的只是經過轉手的摘要，不會被觸發任何想法。查資料是靈感的來源，要研究者自己做。查核者保留的是客觀的第三方立場 |
| 查核者由研究者自己派出、不強制 | 研究者對自己的判斷沒把握時才有用；強迫每一步都查只會變成形式 |
| 查核者要不要每次開新的 | **尚未定案，使用者要再觀察。** 每次開新的沒有包袱、便宜；連續追問同一位有脈絡，但上下文越滾越大，單一查核者的用量可以超過其他全部加起來。不要在簡報或訊息裡替研究者決定 |
| 留言板延後開放、只拉不推 | 同一個模型拿到同一份前提，本來就容易得出同一個「最顯眼」的答案；太早交流會更快收斂。不推送是避免 agent 覺得有訊息就得回 |
| 留言板任何狀態的討論串都列得出來 | 公告型的貼文（發現、死路）如果結案就從列表消失，最有價值的內容壽命反而最短 |
| 討論串由發起者結案並附摘要 | 責任明確；摘要是整輪最後可以重複利用的紀錄 |
| 構築要先報備名稱才能存 | 避免撞名與開太多；主控從註冊表就能看出各單位的方向 |
| 交付文件叫 `docs\build_info.md` | 子 agent 的寫檔工具會拒絕看起來像「報告」的檔名（它要子 agent 把結論放在回傳訊息裡）。這個檔名實測可以寫；被擋時走第 8 步第 6 項 |
| 宣告完成前必須和既有主流玩法比較 | 沒有這一步時，每個單位都只回答「這個前提怎麼配最強」，沒有人回答「這個前提值不值得」 |
| 比較時要修正模擬器不計的機制 | 只比面板數字得出的結論，修正後可以整個反過來。這種修正通常要寫一個小模型，主控可以自己做好放進 `shared\` |
| 重要來源讀不到要回報 | agent 會默默改用別的來源並在筆記裡加一句註記，沒有人上報，結果整輪都少了一個權威來源而沒人知道 |
| 每個 agent 用自己的瀏覽器工作階段名稱 | 共用預設的工作階段時，會互相把對方的頁面導走 |
| 只能用行程編號停止自己的行程 | 研究者下過依程式名稱砍掉全部同名行程的指令（會連其他單位和留言板一起砍），被權限系統擋下 |

## 主控自己容易犯的錯

- **替研究者做決定。** 包括在訊息裡順手加一句操作建議（「查核者請每次開新的」這類）。使用者沒有定案的事不要寫成指示；寫了就更正。
- **處理意外時沒核對歸屬。** 清理某個單位誤寫到別處的檔案時，先確認每個檔案是誰的；搬錯會把一個單位的東西交到另一個單位手上。
- **只轉述、不追查。** 多份報告都出現同一句「某來源讀不到」「未能打開原頁」，就是該停下來查原因的訊號。
- **把研究者的數字當成已驗證。** 沒有重新載入核對過的，回報時要說是自報。
- **拿不同設定下的數字比大小**，或拿模擬器的面板數字去比兩種機制不同的玩法。
- **誤解使用者的用詞。** 遊戲暱稱可能對應兩種東西而答案會因此不同時，先講清楚你採用的是哪個意思。
- **把這一輪的構築結論寫進簡報骨架或這個 skill。**

## 用量

實測（3 個單位；處理量 = 新寫入 + 快取重讀 + 輸出）：

| 一輪的樣子 | 處理量 |
|---|---|
| 各約 40 分鐘（沒有最低時間） | 約 0.6 億 |
| 各 2 小時，有助手 | 約 2.6 億 |
| 各 2 小時，研究者自己查資料加查核者，之後多次叫回 | 約 4.5 億到 5.5 億 |

- 九成以上是快取重讀：agent 每呼叫一次工具就重送整段對話，所以**用量隨單一 agent 的工作長度加速成長**。上下文接近上限時每一步都很貴，自動壓縮之後反而便宜。
- 「窮舉」類的查核請求和被連續追問的查核者是最大的單項支出。
- 交付後每叫回一次，都是在已經很長的上下文上繼續，並不便宜。把要改的事情集中成一次。
- 想控制用量時可以考慮的方向（都還沒有定案，要改先問使用者）：把研究者的工作切段、靠筆記接續；限制窮舉的範圍。
